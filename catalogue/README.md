# Endpoint catalogue

The application embeds the schema-3 master `v3.json` as its offline starter and downloads updates from the [GitHub catalogue channel](https://raw.githubusercontent.com/Shaderx/PingObservatory/catalogue/catalogue/latest.json). Both contain 171 public target definitions and 196 configured family series: 116 numeric-destination and 22 explicitly hostname-level historical successes are verified, while 58 families remain pending without automatic probing. See the [dated evidence and its limits](evidence/README.md). Local measurements start empty. No executable release is published.

The `catalogue` branch contains only reviewed public catalogue data, evidence, documentation and the licence. Its `catalogue/latest.json` is a complete manifest, currently byte-identical to the immutable `catalogue/v3.json` snapshot. Publish a future release by adding its immutable `v<number>.json` snapshot and reviewed evidence, then advancing `latest.json` to that exact higher-version document. Retain earlier snapshots and evidence commits. This allows source development to remain separate from catalogue publication.

An empty URL disables updates. The URL validator permits only this repository's `catalogue/v<number>.json` or `catalogue/latest.json` on `https://raw.githubusercontent.com`, with a single branch, tag or commit ref. Refresh runs at startup and every six hours. A valid newer cache takes precedence over the embedded starter; malformed or older caches fall back visibly to the populated starter. Failed, malformed, oversized, downgraded or same-version conflicting downloads retain the current valid data and cache. The exact earlier preview defaults on `main` migrate to the channel URL when the profile opens; empty and explicit custom or pinned URLs are unchanged.

The 101 derived literal receipts use matching definitions and successes from 2026-10-09, not assumed unchanged configuration at a later date. The other 15 receipts explicitly record their numeric destinations and successful rounds on that date. No historical DNS answer is inferred, and no success from another method or family is substituted. Versioned evidence files are retained; the master pins its evidence object to a Git commit.

## Schema 3

A document contains `schema_version: 3`, a positive JavaScript-safe monotonically increasing `version`, an RFC 3339 `published_at` and a `targets` array. Limits are 4 MiB, 512 targets and 1,024 declared family slots; an oversized update is rejected visibly and never truncated. Fetches have a 15-second bound. Unknown or duplicate fields, trailing documents, invalid versions and invalid identities are rejected. An unavailable or rejected update retains the last valid local catalogue or bundled starter.

Each record retains its stable lowercase `id` (up to 64 characters), positive safe-integer `revision`, `label`, public DNS hostname or IPv4/IPv6 `host`, exact endpoint `port`/`scheme`/`path` when applicable, and intrinsic `measurement` settings. The `manual-` ID prefix is reserved locally. Public provider, category, region, world area, country, tags, approximate location, interpretation and source attribution may be retained. Private targets and operational configuration must be excluded.

Measurement methods are `icmp`, `udp_echo`, `tcp_connect`, `https` and `dns`, with explicit `ipv4`/`ipv6` families and a 60-second schedule. Settings must fit the native collector's supported bounds: ICMP requests may overlap while maintaining their configured spacing, GameLift echo uses port 7770, DNS uses resolver port 53 with explicit expected answers, and HTTPS uses GET or HEAD with expected statuses. The entire cycle must fit within 30 seconds.

Every declared family has an `admission` entry with state `verified`, `unverified`, `unsupported` or `disabled`. A pending state must explain its reason and cannot contain success evidence. It remains visible without automatic probing. A verified family requires `evidence` with an explicit `scope`, exact matching method and family, actual UTC `observed_at` and an HTTPS source URL.

- `scope: "numeric_destination"` requires a numeric `destination`: an IP for ICMP or IP:port for other methods, with bracket notation for IPv6. It forbids `hostname` and `port` fields. The destination family/port must match, and a literal endpoint must equal the observed IP. The 101 derived literal receipts identify their derivation rather than claiming a separately recorded peer field.
- `scope: "hostname"` requires `hostname` exactly matching the configured DNS hostname. It requires the configured `port` for transport/application methods and omits that field for ICMP. It forbids the `destination` field, including empty or null values. It establishes success for that hostname, method and family at the recorded time; the numeric peer was not retained. Published receipts also bind HTTPS scheme, path and HTTP method. A literal endpoint cannot use this scope.

A source review date, deployment date, generic validation label, hostname resolution performed later, synthetic fixture or success from another method/family cannot substitute for a genuine matching observation. The UI labels the evidence scope and missing numeric peer explicitly. Verification records a success from the owner's validation network at that time; it does not guarantee current availability or reachability from a desktop network. Desktop measurements remain separate. Clients resolve and validate their own public numeric destinations for every cycle; curator evidence is never a global replacement for geographic DNS or a runtime destination pin.

## Identity and promotion

An intrinsic probe-definition change (host, port, scheme, path or measurement settings) requires a higher target revision. Display metadata and refreshed admission evidence can change at a higher catalogue version without partitioning historical measurements. Importing curator observations creates no local measurements or destination-change events. A repeated catalogue version must be identical. Removed IDs remain in a bounded persistent revision ledger, so deletion cannot reset their revision. Schema 1 and numeric-only schema 2 remain readable; schema-2 ledger evidence gains its explicit numeric scope during a schema-3 refresh. Older applications reject schema 3 and keep their last-valid v2 cache or starter. A newer embedded schema rejects older cached catalogues and displays a fallback warning rather than downgrading.

Before promotion, obtain only approved public endpoint definitions and genuine ordinary successful observations. Match exact target identity, configured method, family, endpoint, applicable port/path and actual timestamp. Label historical observations and the evidence scope; never invent a numeric peer. Preserve source attribution, increment the document version and review the exact public diff. Do not force probe batches or include credentials, private source addresses, local paths, private history or unrelated infrastructure records. Publish the sanitized manifest to GitHub; applications consume it without a homelab runtime dependency.
